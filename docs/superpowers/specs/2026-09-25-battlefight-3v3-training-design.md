# BattleFight: โหมดฝึกบอท 3v3 แบบเร่งเวลา, Neural Policy และสถิติสำหรับ Tier List

วันที่: 2026-09-25
สถานะ: รอผู้ใช้ตรวจสเปกก่อนทำแผนลงมือ

## เป้าหมายและขอบเขต

สร้างโหมดฝึกแบบ self-play ที่บอท 3 ตัวสู้กับบอท 3 ตัวโดยไม่มีผู้เล่นมนุษย์ ใช้กติกา แผนที่ ตัวละครหกตัว อาวุธ สคริปต์ ฟิสิกส์ และข้อจำกัดทรัพยากรเดียวกับเกมปกติ โหมดฝึกเริ่มและหยุดด้วยคำสั่งแยก ไม่เริ่มเองเมื่อเปิดเกม ผลการฝึกและสถิติคงอยู่หลังรีสตาร์ต ผู้ใช้ปรับจำนวนแมตช์ที่จำลองพร้อมกันได้ และให้ worker เร่งเวลาจำลองเมื่อผ่านการตรวจความเทียบเท่าของเกม เป้าหมายหลักของการเรียนรู้คืออัตราชนะทีม 3v3

ผลลัพธ์อีกส่วนคือข้อมูลดิบที่ตรวจย้อนหลังและส่งออกเป็น JSON/CSV สำหรับทำ tier list ภายหลัง รุ่นแรกไม่สร้างอันดับ S/A/B อัตโนมัติ การประเมินรุ่นใช้ผล self-play เป็นเกณฑ์เดียวที่มีอยู่ในตอนนี้ โดยระบุชัดว่าความก้าวหน้าเป็นความเก่งเมื่อเจอบอทในชุดทดสอบ ไม่ใช่ผลวัดกับมนุษย์

## สภาพปัจจุบันและขอบเขตการแก้

เกมรันจาก `taro-engine/src/game.json` ผ่านเซิร์ฟเวอร์ Taro เดิม บอทผู้เล่นสองตัวถูกสร้างใน `GameComponent` ตอนเริ่มเกม และสมองปัจจุบันเลือกโจมตีเฉพาะมนุษย์ เซิร์ฟเวอร์ HTTP ใช้พอร์ต 80 แบบตายตัว และเกมแต่ละโปรเซสมีสถานะ `ige` แบบ singleton ดังนั้นการจำลองหลายแมตช์ในโปรเซสเดียวจะปะปนกัน

โหมดฝึกจึงต้องมีเส้นทางเริ่มเกมแยก: ไม่สร้างบอทสองตัวแบบแมตช์ปกติ ไม่เปิดให้มนุษย์เข้าร่วม ไม่ยึดพอร์ต 80/2001 ของเกมปกติ และให้บอทเลือกคู่ต่อสู้ฝั่งตรงข้ามได้เฉพาะในโหมดฝึก การแยกนี้ต้องไม่เปลี่ยนการหาเป้าหมายหรือคะแนนของแมตช์ปกติ

## โครงสร้างโปรเซสและการควบคุม

ตัวควบคุมการฝึก (supervisor) เปิด worker หลายโปรเซส; หนึ่ง worker ถือเกม 3v3 หนึ่งแมตช์พร้อมสถานะ Taro/ฟิสิกส์ของตัวเอง Worker ใช้เส้นทาง headless ไม่ผูก HTTP/เกมพอร์ตสาธารณะและไม่ติดต่อ backend ที่ไม่จำเป็น แต่ยังรัน game loop, collision, item scripts, death/respawn และการจบแมตช์จริง ตัวควบคุมหลักจัดคิวคู่แข่ง/ตัวละคร/seed, จำกัดจำนวน worker, รับผลและ trajectory การเรียนรู้, และเป็นผู้เขียนข้อมูลถาวรเพียงรายเดียว ตัวฝึก neural network เป็น optimizer แยกจาก worker เกม เพื่อไม่ให้การอัปเดตน้ำหนักกระทบลูปฟิสิกส์

คำสั่งที่ต้องมีใน `taro-engine`:

- `npm run train:3v3 -- --workers N --speed max|realtime` เริ่มหรือดำเนินการฝึกต่อจาก checkpoint; ค่าเริ่มต้น `min(4, max(1, availableParallelism - 1))`, อนุญาต `1..8`, ค่า speed เริ่มต้นเป็น `max` หลังผ่าน parity gate
- `npm run train:status` ดูจำนวนแมตช์ ความเร็ว รุ่นหลัก รุ่นทดลอง อัตราชนะ และข้อผิดพลาดล่าสุด
- `npm run train:stop` หยุดรับงานใหม่ รอแมตช์ที่กำลังเล่นจบ แล้วบันทึกผล; หากเกินเวลารอที่กำหนดให้ทำเครื่องหมายแมตช์ค้างว่า `aborted` และไม่ใช้เลื่อนรุ่น
- `npm run train:auto -- on|off` ตั้งค่าการใช้รุ่นใหม่ในเกมปกติอัตโนมัติ โดยค่าเริ่มต้นเป็น `off`
- `npm run train:activate -- <version>` เลือกรุ่นที่ตรวจแล้วด้วยตนเอง และ `npm run train:rollback` กลับรุ่นก่อน
- `npm run train:export -- --format json|csv` ส่งออกข้อมูล tier-list โดยแยกตามรุ่นบอท

คำสั่งเริ่มต้องมี lock ป้องกัน supervisor สองตัวเขียนคลังผลเดียวกัน และตรวจ PID/instance id ก่อนจัดการ lock เก่าหรือสั่งหยุด โปรเซสฝึกแยกจากเกมปกติแต่ยังใช้ CPU/RAM เครื่องเดียวกัน; จำนวน worker ต้องลดได้ทันทีในการเริ่มครั้งต่อไป และไม่รับประกันว่าการเพิ่ม worker จะเร็วขึ้นอย่างไม่จำกัด ต้องรายงานอัตรา `simulated seconds / wall-clock second` จริงใน status

## เวลาเร่งและความเทียบเท่าของเกม

ใน worker ฝึกให้ขับฟิสิกส์ด้วย fixed timestep 1/60 วินาทีและขับสมองบอททุก 6 ขั้น (10 Hz) โดยไม่รอเวลาโลกจริง งานหน่วงเวลาในสคริปต์ อายุ projectile, cooldown, respawn, การฟื้นฟูพลัง และเวลาจบรอบต้องอ่านนาฬิกาจำลอง/คิว timer เดียวกัน ส่วนเวลาโลกจริงใช้เฉพาะ timeout ของ supervisor, การวัด CPU และการเขียน log ห้ามใช้ `ige.timeScale()` เพียงอย่างเดียว เพราะโค้ดปัจจุบันมีทั้ง `Date.now()`, `ige.now` และ `setTimeout()` ที่เป็นเวลาจริง

ก่อนอนุญาตให้ผลโหมด `max` ใช้ฝึกหรือเลื่อนรุ่น ต้องรันแมตช์ seed/นโยบาย/ทีมเดียวกันในโหมด `realtime` และ `max` แล้วเปรียบเทียบลำดับการใช้สกิล การชน/ชิ่ง ความเสียหาย การตาย คะแนน และผลแพ้ชนะ พร้อม tolerance เฉพาะตำแหน่งลอยตัว หาก parity ไม่ผ่าน ให้บันทึกเป็นข้อผิดพลาดและใช้ `realtime` ชั่วคราวจนแก้ ไม่เอาผลเร่งที่ผิดกติกามาเลื่อนรุ่น โหมด `max` เร่งด้วยการทำหลาย fixed steps ต่อเวลาจริงหนึ่งช่วง ไม่เปลี่ยนค่ากฎฟิสิกส์หรือขนาด timestep

## แมตช์ฝึกและนโยบายบอท

หนึ่งแมตช์มีหกผู้เข้าร่วมจริง ทีมละสาม แต่ละบอทมียูนิตต่อสู้ที่ใช้งานได้ไม่เกินหนึ่งตัว ไม่มี NPC/ผีถูกนับเป็นผู้เล่นที่ยังมีชีวิต ใช้ระบบทีม คะแนน การตาย และเกิดใหม่ของเกม โดยกำหนดรูปแบบ TDM 3v3 ให้ชัดใน training mode จบรอบเมื่อกติกาชนะของ TDM เกิด หรือเมื่อครบเวลา 5 นาทีโดยตัดสินจากคะแนนทีม; คะแนนเท่ากันเป็นเสมอ ไม่มีการยิงเพื่อนร่วมทีมหรือเลือกบอททีมเดียวกันเป็นเป้าหมาย

ตัวละครทั้งหกถูกสุ่มแบบกระจายโอกาสให้ใกล้เคียงกัน และบันทึกชุดตัวละครของทั้งสองทีม การประเมินรุ่นทดลองต้องสลับฝั่งพร้อมใช้ชุดตัวละคร/seed จับคู่กันเพื่อลดความเอนเอียงจากจุดเกิดและแผนที่ การสุ่มเป็นตัวช่วยความหลากหลาย ไม่เปิดข้อมูลลับของฝ่ายตรงข้ามให้สมองบอท

นโยบายที่ฝึกได้มีสองชนิด: (1) ค่ากลยุทธ์ที่มีช่วงปลอดภัย เช่น น้ำหนักเลือกเป้าหมาย ระยะยืน ระดับเลือดที่ถอย ระยะห่างเพื่อนร่วมทีม การจัดลำดับอาวุธ/สกิล และเกณฑ์หลบ/ไล่; (2) neural policy ขนาดเล็กที่เรียนรู้การจัดลำดับตัวเลือกยุทธวิธีจากข้อมูลที่บอทสังเกตได้ ทั้งสองชนิดต้องมี version และไม่ปรับเลือด ดาเมจ ความเร็วเคลื่อนที่ ความเร็วกระสุน ทรัพยากร หรือคูลดาวน์ และไม่ข้ามระบบควบคุม/อาวุธเดิม รุ่นเริ่มต้นคือพฤติกรรมบอทปัจจุบัน

Neural policy รับ observation ที่ระบุสัญญาแน่นอน ได้แก่ ตำแหน่ง/ความเร็ว/เลือดที่สังเกตได้ของตน เพื่อน และศัตรู แผนที่กำแพง กระสุนที่สังเกตได้ อาวุธ/คูลดาวน์ของตน และตัวเลือกทางยิงที่ผ่านการตรวจแล้ว เอาต์พุตคือคะแนนของตัวเลือก เช่น เป้าหมาย ทิศทางเคลื่อนที่ ช่องอาวุธ และจุดเล็ง ไม่ส่งคำสั่งดิบข้ามข้อจำกัดเกม มี action mask ตัดตัวเลือกที่ยิงไม่ได้ ใช้ทรัพยากรไม่พอ หรือทำให้โจมตีเพื่อนร่วมทีม โมเดลเดียวใช้ร่วมกันทั้งหกตัวโดยมีรหัสตัวละครใน observation; benchmark เทียบกับกลยุทธ์เดิมก่อนเลื่อนรุ่น

การฝึก neural network ใช้ trajectory จาก worker ผ่าน optimizer แบบ PPO พร้อม team-win reward เป็นหลัก และใช้สัญญาณ damage/assist/survival ที่มีน้ำหนักรองเพื่อให้เรียนรู้ก่อนจบเกม ติดตั้ง Python 3 กับ PyTorch ในสภาพแวดล้อมแยกสำหรับ optimizer (เครื่องปัจจุบันยังไม่มี `python` ใน PATH) แล้วส่งออกน้ำหนัก MLP เป็นไฟล์ versioned สำหรับ inference ขนาดเล็กใน Node worker/เกมปกติ ต้องมี golden-vector test ยืนยันว่า inference ฝั่ง Node ให้ผลตรงกับ optimizer และมี baseline heuristic เป็น fallback เมื่อโมเดลโหลดไม่ได้หรือประเมินแล้วไม่ดีขึ้น

## การเล็งกระสุนชิ่งกำแพง

เพิ่มตัวเลือกเล็งชิ่งหนึ่งครั้งสำหรับอาวุธที่ข้อมูลจริงอนุญาตให้ projectile ชนกำแพงโดยไม่ถูกทำลายและมี restitution มากกว่า 0 เช่น Alchemist's Bouncing Bullet (`ICKyoWSGCI` ในข้อมูลเกมปัจจุบัน) ตัวสร้างทางยิงใช้ตำแหน่ง/ความเร็วเป้าหมายที่สังเกตได้ ความเร็วกระสุน อายุ projectile ขอบกำแพง และค่าสะท้อน เพื่อเสนอจุดเล็งที่มีวิถีถึงเป้าหลังชิ่ง แล้วให้ heuristic หรือ neural policy เลือกระหว่างยิงตรง ชิ่ง หรือไม่ยิง ต้องตรวจว่าจุดชนและทางวิถีไม่ถูกกำแพงอื่นขวาง และไม่ถือว่ากระสุนธรรมดายิงทะลุกำแพงได้

บันทึก wall-bounce, ricochet shot, ricochet hit และ damage หลังชิ่งเป็นเหตุการณ์แยกกัน การชนกำแพงเพียงอย่างเดียวไม่ใช่ hit หรือ damage; damage จะนับเมื่อกระสุนหรือสกิลลดเลือดศัตรูจริงหลังจากนั้น ฟิสิกส์จริงของเกมเป็นผู้ตัดสินว่ากระสุนชิ่งและโดนหรือไม่ ตัวคาดการณ์มีหน้าที่ตัดสินใจเล็งเท่านั้น

## วงจรเรียนรู้และเลื่อนรุ่น

Supervisor สร้าง candidate แบบปรับค่ากลยุทธ์และแบบ neural policy แล้วให้แข่งกับ champion และกลุ่มรุ่นเก่าที่เก็บไว้ Neural optimizer ฝึกจากแมตช์ training เท่านั้นและ publish snapshot เมื่อครบ batch โดยไม่แก้น้ำหนักกลางแมตช์ แยกแมตช์ training ออกจาก validation ที่เลือก seed/ทีมไว้ล่วงหน้าและไม่ใช้ปรับ candidate ระหว่างรอบนั้น ผลชนะนับ 1 แพ้นับ 0 เสมอนับ 0.5 เฉพาะแมตช์ที่จบถูกต้อง

หลังมีอย่างน้อย 30 คู่แมตช์ที่สลับฝั่งกับ champion (60 เกม) จึงพิจารณาเลื่อนรุ่น ต้องมีขอบล่างของช่วงความเชื่อมั่น 95% จาก paired bootstrap ของคะแนนแมตช์สูงกว่า 50% และไม่มีการถอยอย่างชัดเจนเมื่อเจอรุ่นเก่าหรือ baseline ตรึงไว้ การ bootstrap ใช้ seed คงที่เพื่อให้ผลประเมินซ้ำได้ ถ้าหลักฐานไม่พอ ให้เก็บ candidate/ผลไว้แต่ไม่เลื่อนและฝึกต่อหรือสร้าง candidate ใหม่ การชนะกันเองระหว่าง candidate สองฝั่งอย่างเดียวไม่ถือว่าเก่งขึ้น

Champion, candidate, baseline และประวัติรุ่นเก่าเก็บเป็นไฟล์ versioned ที่ตรวจ schema และ checksum ก่อนโหลด การเลื่อนรุ่นเขียน checkpoint ใหม่แบบ atomic โดยเก็บรุ่นก่อนสำหรับ rollback หาก worker ล้ม แมตช์ timeout หรือผลไม่สมบูรณ์ ให้ retry แบบมีขอบเขตและทำเครื่องหมายผลผิดพลาด; ผลเหล่านี้ไม่เข้าตัวหาร win rate หรือสถิติ tier list ที่เผยแพร่ หากเขียนข้อมูลไม่สำเร็จให้หยุดการเลื่อนรุ่นและรายงานข้อผิดพลาด แทนการฝึกต่อโดยไม่มีหลักฐาน

## การใช้รุ่นใหม่ในเกมปกติ

ตั้งค่า `auto-update` ถาวรและเริ่มต้นเป็น `off` หากปิด ผู้ใช้เลือก champion ที่จะใช้งานด้วย `train:activate`; หากเปิด เกมปกติรับ champion ใหม่ที่ผ่านเกณฑ์เมื่อเริ่มแมตช์/รอบถัดไปเท่านั้น ไม่เปลี่ยนนโยบายของยูนิตที่กำลังต่อสู้ หากโหมดเกมไม่มีขอบเขตรอบที่ปลอดภัย ให้รอการเริ่มเซิร์ฟเวอร์เกมครั้งถัดไปแทน รุ่นที่กำลังใช้งานต้องถูกบันทึกแยกจากรุ่นล่าสุดที่ฝึกได้ เพื่อให้ตรวจและ rollback ได้ทั้งสองโหมด หากไฟล์ policy เสีย/อ่านไม่ได้ ให้ใช้รุ่นล่าสุดที่ตรวจแล้วหรือ baseline และแจ้งสถานะ ไม่ทำให้เกมปกติหยุด

## ข้อมูลสถิติและการส่งออก

Worker ส่งสรุป event ที่ระบุ `matchId`/`eventId`; supervisor deduplicate แล้ว append ผลรายแมตช์เป็น JSONL และอัปเดต checkpoint แบบ atomic ใน `taro-engine/training-data/` ซึ่งไม่อยู่ใน Git ข้อมูลขั้นต่ำ:

- แมตช์: schema version, เวลาจริง/เวลาจำลอง, duration, speed mode/factor, seed, map/game-data hash, policy kind/version แต่ละฝั่ง, ชุดตัวละคร, ฝั่ง, คะแนน, winner/draw, สถานะ complete/aborted/error
- ผู้เล่นบอทต่อแมตช์: ตัวละคร, ทีม, policy version, เวลาเล่น, win/loss/draw, kills, deaths, assists, damage dealt/taken, เวลารอดชีวิต และจำนวนครั้งเกิด
- อาวุธต่อบอท: item type, จำนวนครั้งใช้จริง, จำนวนการโดนศัตรูที่ยืนยันด้วย damage event, damage ที่ทำ, จำนวนครั้งชิ่งกำแพง, จำนวนยิงแบบชิ่ง, จำนวนโดนหลังชิ่ง และ damage หลังชิ่ง; แยกการโจมตีแบบพื้นที่/หลายเป้าหมายไม่ให้นับการกดหนึ่งครั้งเป็นหลายครั้งใช้

Kills/deaths ต้องนับไม่เกินหนึ่งครั้งต่อชีวิต Assists นับผู้ที่ทำ damage ต่อเป้าหมายใน 10 วินาทีก่อนตายโดยไม่ใช่ผู้ได้ kill และไม่ใช่ฝ่ายเดียวกัน Damage ต้องมาจากผลที่ลดเลือดจริง ไม่ใช่แค่ projectile สัมผัสกำแพงหรือการกดใช้ไอเท็ม; ถ้ากระสุนชิ่งกำแพงแล้วลดเลือดภายหลัง ให้นับ damage ณ การโดนเป้าหมายและผูกกับ projectile เดิม ข้อมูลสรุปสำหรับ tier list แยก policy kind/version, ตัวละคร, ชุดทีม, ฝั่ง และจำนวนตัวอย่าง; ค่าเฉลี่ยและ win rate ต้องแสดงตัวหารเสมอ ผลฝึกและ validation แยกกันในการส่งออก ห้ามรวมแบบเงียบ ๆ รุ่นแรกส่งออกข้อมูล ไม่ตัดสิน tier อัตโนมัติ

## การตรวจรับ

1. เปิดเกมปกติและฝึกพร้อมกันได้โดยไม่แย่งพอร์ต; เกมปกติยังมีบอทสองตัวตามเดิม ส่วน worker มี 3v3 จริงและไม่มีมนุษย์
2. รัน worker 1 และมากกว่า 1 ตัวแล้วได้แมตช์แยกกัน ผลรวมไม่ซ้ำ/ไม่สูญหาย; ทดสอบหยุดอย่างสุภาพและกรณี worker crash/retry
3. ทดสอบการคิดคะแนน ตาย เกิด ฆ่าตัวเอง ความเสียหายพื้นที่ เสมอ และ timeout ของแมตช์ฝึก; ไม่มีการยิงทีมเดียวกันหรือยิงหลังตาย
4. ทดสอบ candidate ชนะ/แพ้/หลักฐานไม่พอ/ผลผิดพลาด ว่า promotion ถูกต้อง และ checkpoint อยู่รอดหลังรีสตาร์ต/rollback
5. ทดสอบ `auto-update` ทั้งสองค่า: รุ่นเกมปกติเปลี่ยนเฉพาะขอบเขตรอบใหม่; นโยบายเสียหายต้อง fallback โดยไม่ล้มเกม
6. ตรวจ JSON/CSV ด้วยผลแมตช์ที่ทราบคำตอบแน่นอน โดยเฉพาะ kills, assists, damage, weapon hits, ตัวหาร win rate และการแยก policy version
7. รันฝึกหลาย worker ต่อเนื่องอย่างน้อย 15 นาที วัด throughput, CPU/RAM, จำนวนยูนิต/โปรเซส/งานหน่วงเวลาคงค้าง พร้อมรัน smoke และ compatibility tests เดิม
8. ทดสอบ projectile ที่ชิ่งได้กับกำแพงจริง: เล็งหนึ่งชิ่งแล้วโดนศัตรู, ชิ่งแล้วพลาด, ชนกำแพงหลายครั้ง, หมดอายุ, และอาวุธที่ถูกทำลายเมื่อชนกำแพง; ตรวจว่า damage/hit นับเฉพาะเมื่อเลือดลด
9. ทดสอบ virtual clock กับ cooldown, timeout สคริปต์, projectile lifespan, respawn, regeneration และคะแนน โดยเทียบ `max` กับ `realtime` จาก seed เดียวกัน; รายงาน speedup ที่วัดได้จริงและห้ามใช้ผล `max` ที่ parity ไม่ผ่านเลื่อนรุ่น
10. ทดสอบ neural policy ตั้งแต่ trajectory ถึง checkpoint, golden-vector inference, action mask, train/eval split, restart/resume และ fallback; เลื่อนรุ่น neural เฉพาะเมื่อชนะ heuristic/champion ใน self-play validation ตามเกณฑ์เดียวกัน

## สิ่งที่ยังไม่รวม

ไม่สร้างหน้าจอ tier list, ไม่เปลี่ยนค่าสมดุลตัวละคร และไม่อ้างว่าชนะผู้เล่นเก่งจากผล self-play เพียงอย่างเดียว เพราะขณะนี้ไม่มีผู้เล่นอื่นให้ทดสอบ ผล self-play เป็นเกณฑ์ที่ใช้จริงสำหรับเลื่อนรุ่นและทำ tier list ในขอบเขตนี้
